# 架构与可靠性设计

## 设计原则

1. **AI 负责理解判断，代码负责执行验证**：AI 读消息、抽字段、判断存不存；调用 115、写目录、去重都由确定性代码完成，转存后读回核验。
2. **稳定内核 + 可插拔外围**：主流程是固定骨架，能力都是挂在扩展点上的插件（见 [插件开发指南](plugins.md)）。
3. **单一 Context 贯穿全程**：一条消息带着 `PipelineContext` 流经所有阶段，每次状态变更都持久化，可追溯、可恢复、可干预。
4. **失败隔离**：通知和事件先落库再独立投递；转存前置检查和整理失败会阻止任务完成，但不会拖垮其他任务。

```
 Telegram 消息 ──▶ 监听（Source）──▶ 落库 received
                                      │  Worker
                                      ▼
            before_parse ─▶ 解析（Parser）─▶ after_parse（TMDB…）─▶ 确定性置信度 ─▶ 决策（Decision）
                                                                              │
                                    ┌─────────────── pending_approval ◀── ask ┤── skip ─▶ rejected / skipped
                                    │ 人工批准                                 │ save
                                    ▼                                          ▼
            before_save（分类路由）─▶ 准备清单 ─▶ 转存（Storage）─▶ 读回核验 ─▶ after_save（整理、STRM）─▶ done
```

## 任务状态机

```
received → parsed → pending_approval → queued → saving → stored → organizing → done
                └→ queued / rejected / skipped    └→ need_manual       └→ need_manual
解析或转存准备失败 → failed → 从记录的阶段重试（按 not_before 退避，不占并发槽）
```

- **审批态落库**：待确认任务持久化为 `pending_approval`，按钮 callback 只带任务 ID，进程重启后仍可点。
- **三层去重**：消息级（来源 + 消息 ID）、资源级（存储 Provider + 目标 CID + 分享码）、内容级（存储 Provider + 目标 CID + 标题 + 季 + 集）。剧集按集去重，同一分享链接追更新增的集仍会转存。
- **确定性校验失败**（集号无法识别、多季未指定、电影有多个正片候选）在转存前停止，任务标记为不自动重试，修正后人工重试。

## 识别

- 调用 LLM 前先做确定性预过滤（无 115 链接、黑名单、缺 must_have），相同正文命中缓存，瞬时错误退避重试，非法输出重试一次；仍失败则降级 regex 并强制人工确认。
- 分享码与访问码只由确定性代码从正文和超链接中提取，不采信 LLM。
- 置信度由标题/类型/年份/TMDB 匹配等可核对信号计算（`reelay/core/confidence.py`），LLM 自报值仅保存在 `raw_fields.parser_confidence`。
- TMDB 按标题相似度与年份打分，最佳候选不可信时不改标题并转人工。

## 转存与恢复边界

`StorageProvider` 分为 `prepare`（列出分享、确定文件清单、建立独占暂存目录）、`save`（发送一次转存）、`reconcile`（只读核验）：

- 分享清单是集数的事实来源：剔除样片/预告/花絮，按文件名识别季集，排除目标目录中已入库的集。
- 文件清单和 `receiving` 检查点必须在调用 115 写接口之前提交。115 没有可用的请求幂等键，发送前后中断时无法确认是否已执行，所以 `receiving` 恢复后**只核验、绝不重发**；空目录、部分落地、内容不符都进入 `need_manual`，由管理台"核验转存"重新读回。
- 落地文件按名称、数量、大小与可用 SHA1 完整核验，分别记录源文件与落地文件 ID。转存回执、去重记录与释放资源占位在同一事务内提交，之后整理可独立恢复。
- 资源占位（分享与集）在准备阶段获取；集数确定后如需占用的集正被其他任务持有，会释放全部占位再排队，避免互相等待；发送前重新核对其他任务是否已入库同一内容。
- 整理先持久化计划，再按文件 ID 执行建目录/改名/移动并读回核验；中断后按文件实际位置续跑。同名冲突按 `organize.conflict` 处理，删除动作先记入扩展状态，重放不会重复删除。
- SQLite 使用 WAL + FULL 同步；数据库结构以 `PRAGMA user_version` 版本化迁移，版本高于程序时拒绝打开。

## 通知、事件与告警

- 通知与事件使用事务 Outbox：与任务状态在同一事务内写入，投递器独立重试（单次 30 秒超时，最多 8 次，支持 Telegram FloodWait），至少一次语义。已处理的审批和旧轮次通知不再推送。
- 系统通知（故障告警与恢复、审批汇总、日报）同样走 Outbox，进程重启不丢。告警按类别去重：状态由正常变为异常时通知一次，恢复时发送恢复通知。
- 115 cookie 缺失或失效时暂停转存与整理的领取（解析照常），任务回到原阶段等待，不消耗重试次数，凭证恢复后自动继续。
- 消息源断开超过阈值告警；重连后按每个来源已接收的最大消息 ID 补拉停机期间的消息。

## 配置与快照

任务接收时保存审批、过滤、转发、路由、命名和扩展开关的配置快照：配置更新只影响新任务；"重新解析"使用当前策略，"重新整理"使用当前命名与扩展配置。目录别名在尚无转存检查点时解析为当前 CID，有检查点后绑定原 Provider、CID、清单与文件 ID。

## 进程模型

- `python -m reelay.main`：消息源 + Worker + 控制 Bot，单实例（数据库旁的文件锁阻止两个 Worker 消费同一数据库）。
- `python -m reelay.web`：管理 API 与前端，只读写任务状态，不启动 Worker。
- `python -m reelay.mcp_server`：MCP 接入，与 Web 相同的服务层。

三者共享同一个 SQLite 数据库与配置文件；Web/MCP 修改配置后，Worker 约 1 秒内采用。
